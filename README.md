# Sub-Merchant Improvement — Paydia Mockup

A single-file, four-platform interactive mockup (Login, Registration, Web
Merchant, Admin Internal Dashboard) for the Paydia sub-merchant improvement
project. There is no framework, no build tooling beyond one Node script, and
no `package.json` — everything lives in vanilla HTML/CSS/JS inside
`mockup.html`.

## Files

- `mockup.html` — the plaintext source of truth. Edit this file, never
  `index.html` directly.
- `build_protected.js` — reads `mockup.html`, strips the old client-side login
  gate, inlines `versions.js`, AES-256-GCM/PBKDF2-encrypts the result, and
  writes `index.html`.
- `versions.js` — the in-app version picker shown in the dev bar. Inlined into
  `index.html` at build time (see below) — it is never linked from
  `mockup.html` in the deployed output, since `.vercelignore` only serves
  `index.html` publicly.
- `index.html` — the encrypted build artifact actually served in production.
  **Never hand-edit this file.** It is fully regenerated by
  `build_protected.js` and any manual edit will be silently lost (and will
  drift from `mockup.html`) the next time someone runs the build.
- `VERSION` — single line, current version number.
- `CHANGELOG.md` — Keep a Changelog / SemVer changelog, and the authoritative
  description of the release ritual.

## Build

```
node build_protected.js
```

Regenerates `index.html` from `mockup.html`. Run this after every edit to
`mockup.html` or `versions.js`, before committing and before deploying.
Expect a `[OK] Encrypted build written to index.html` line with no errors.

## Deploy

```
vercel --prod
```

Project name: `sm-mockup`. `.vercelignore` restricts the publicly served
files to `index.html` plus two sample images — the plaintext source,
requirement docs, and screenshots never leave this machine.

## Release ritual

See `CHANGELOG.md` for the full step-by-step ritual. In short: every change,
however small, gets a CHANGELOG entry, a `VERSION` bump, a `versions.js`
entry, a rebuild, a commit, a `vX.Y.Z` tag, a `git push --follow-tags`, and a
deploy — then the deployed version's `deployed` flag is flipped to `true`
(only after the deploy actually succeeds) and committed as a small follow-up.

## Never hand-edit `index.html`

`index.html` is a generated, encrypted artifact. It is committed to git so
the deployed state is reproducible and auditable, but it is not source code
— it is the *output* of `build_protected.js` run against `mockup.html`. Any
change belongs in `mockup.html` (or `versions.js`), followed by a rebuild.
